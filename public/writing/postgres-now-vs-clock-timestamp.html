NOW() is not now

13 August 2026 · Postgres

A distributed lock that silently stops working the moment you pass it a transaction — and reads perfectly correct while it does.

Node schedulers start their jobs in every replica. node-cron and friends have no idea another copy of your process exists, so the moment you run two containers, both fire the same tick. An in-process running flag does nothing about it — it only prevents overlap within one process. If the job sends email or charges cards, you now do that twice.

The fix, if you already have Postgres, is a lease: one row per job, claimed by a single conditional upsert. Whoever writes the row runs the tick, everybody else gets nothing back and skips. 

INSERT INTO cron_leases (job_name, lease_until, holder)
VALUES ($1, NOW() + ($2 * interval '1 millisecond'), $3)
ON CONFLICT (job_name) DO UPDATE
  SET lease_until = EXCLUDED.lease_until,
      holder      = EXCLUDED.holder
  WHERE cron_leases.lease_until <= NOW()
RETURNING job_name

The WHERE on the DO UPDATE is the whole mechanism. Without it every replica overwrites the row and all of them run. With it, the update only applies when the stored lease has already expired, so exactly one claimant gets a row back.

Every timestamp comes from the database rather than from a replica, which is the point — the machines never compare their own clocks to anything, so skew between them cannot produce two winners.

That query has a bug. It took me a while to see it, and longer to believe it.

NOW() is frozen

NOW() in Postgres is an alias for transaction_timestamp(). It returns the moment the surrounding transaction started, and it returns that same value for the rest of the transaction no matter how long it runs. This is documented, entirely intentional, and the correct default for most things — it is what makes every row in one transaction agree about when "now" was.

It is exactly wrong for a lease. The whole design rests on reading the database's current wall clock, and inside a transaction that has been open for a few seconds, NOW() is not the current wall clock. It is history.

The lease looks fine in every test, because a test calls it on a pool, where each statement is its own transaction and NOW() is always fresh. The bug needs a caller who passes a transaction handle — which is a perfectly reasonable thing to do, and which somebody eventually does.

Watching it happen

This is the kind of claim worth proving rather than reasoning about, so I opened a transaction against a real database, sat in it, and asked both functions what time it was. 

BEGIN;
SELECT pg_sleep(3);
SELECT clock_timestamp() - now() AS now_is_stale_by;

 now_is_stale_by
-----------------
 00:00:03.006

Three seconds of drift, and it grows for as long as the transaction stays open. Now put a lease in front of it. Claim one that expires in 60 ms, wait it out, then try to re-claim from inside a transaction that has been open for three seconds: 

-- lease_until is 60ms in the past. It has genuinely expired.
-- Inside a 3s-old transaction:

  WHERE cron_leases.lease_until <= NOW()              -- false. 0 rows. Skipped.
  WHERE cron_leases.lease_until <= clock_timestamp()  -- true.  1 row.  Claimed.

The lease had expired. The row was free. And the claim returned nothing, because it compared a present-tense fact against a past-tense clock.

Why this one is nasty

The failure is bad in both directions, and neither direction announces itself.

  • The comparison is stale, so an expired lease reads as still held. Every replica skips. The job stops running — not with an error, but by unanimously and correctly deciding somebody else has it. Your monitoring sees a healthy fleet doing nothing.
  • The expiry it writes is stale too. NOW() + interval anchors the new lease to when the transaction opened, so a lease meant to reserve the next fifty minutes expires fifty minutes after a moment that has already passed. A second replica can claim inside the window you thought you had reserved — reintroducing the duplicate run you installed the lease to prevent.

And it is invisible until the exact conditions line up: a caller passing a transaction, that transaction being open long enough to matter, and a lease near its boundary. Unit tests on a pool will never see it. It waits for production, where transactions are longer and the boundaries get hit constantly.

The fix

clock_timestamp() reads the actual current time, every call, transaction or not. Four occurrences — both writes and both comparisons: 

INSERT INTO cron_leases (job_name, lease_until, holder, claimed_at)
VALUES ($1, clock_timestamp() + ($2::bigint * interval '1 millisecond'), $3, clock_timestamp())
ON CONFLICT (job_name) DO UPDATE
  SET lease_until = EXCLUDED.lease_until,
      holder      = EXCLUDED.holder,
      claimed_at  = clock_timestamp()
  WHERE cron_leases.lease_until <= clock_timestamp()
RETURNING job_name

Postgres gives you four of these and the differences matter: transaction_timestamp() (which is NOW()) is fixed for the transaction; statement_timestamp() is fixed for the statement; clock_timestamp() moves continuously; and timeofday() is the same as clock but returns text. Anything that reasons about elapsed real time wants clock_timestamp(), and almost everything else wants NOW().

The general lesson is smaller than the bug: the safe-looking default is safe because it makes a transaction internally consistent, and a lock is one of the few things that needs to see outside its own transaction. When a query's correctness depends on real elapsed time, the frozen clock is the wrong instrument, however natural NOW() reads.

This came out of pg-cron-lease, a small package that does the above and nothing else. Its integration suite races ten claimants at one occurrence against a real Postgres, and pins this behaviour by claiming from inside a deliberately long-open transaction — because a regex over a SQL string cannot tell you whether the SQL works.
