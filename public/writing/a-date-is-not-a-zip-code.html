2024-01-15 is not a ZIP code

13 August 2026 · Data

It geocodes anyway — to a real point on the National Mall — and nothing downstream can tell that answer from a correct one.

Resolving a US ZIP code to coordinates offline is a small problem. You ship the Census ZCTA Gazetteer, about 33,000 rows of zip,lat,lng, and look it up. No geocoder, no API key, no per-request fee, and — often the actual reason — the address never leaves your infrastructure, which is a data-sharing decision as much as a technical one.

The lookup is the easy half. The parsing is where this goes wrong.

Five digits is a very low bar

The obvious implementation pulls the first five digits out of whatever it is handed. Watch what that does to input that is not a ZIP code:

InputNaive resultWhere that is
'2024-01-15'20240Washington, DC
'Suite 200, 123 Main St'20012Washington, DC
'404-555-1234'40455Kentucky
'order #98 qty 7654'98765Washington state

A date and a street address both land in DC. Those are not errors that fail — they are real ZCTAs with real centroids, and they come back as ordinary successful lookups.

A wrong coordinate is worse than no coordinate, because downstream it is indistinguishable from a right one. A null is a question. A point on the National Mall is an answer, and everything after it — the distance sort, the radius filter, the map pin — treats it as fact.

What actually counts as a ZIP

The fix is to stop pattern-matching for digits and start recognising shapes. Three of them are legitimate; everything else is a null:

  1. The whole value is a ZIP or ZIP+4. '30305', '30305-1234', '303051234'.
  2. Digits and separators only, at exactly 5 or 9 digits — '3 0 3 0 5'. Somebody reading their ZIP aloud produces this. The digit count is what does the work: a phone number has ten and a date has eight, so both fall out rather than being truncated to fit.
  3. A delimited five-digit run inside prose — 'Atlanta, GA 30305'. Delimited matters: 'Suite 200, 123 Main St' has no five-digit run that is not butted against other digits, so it is a null rather than 20012.

Everything about that list is about refusing plausible input. It is a strange thing to optimise for until you have shipped the alternative.

The leading-zero asymmetry

There is one case where guessing is correct, and it is the one people usually get backwards.

Northeastern ZIP codes start with zero, and the moment anything treats one as a number the zero is gone. 01001 — Agawam, Massachusetts — comes out of a numeric column as 1001. Read that as a prefix and you get 100, which is New York: the wrong state, and a plausible-looking one.

So a number gets padded, because recovering the zero is lossless rather than a guess:

normalizeZip(1001)     // '01001'  — a number cannot carry a leading zero
normalizeZip('1001')   // null     — a string of four digits is a typo

Same digits, opposite treatment, and both are right. An integer 1001 can only have meant 01001; there is no five-digit ZIP whose numeric value is 1001 and no other reading. A string '1001' arrived as text through something that preserves zeros, so its four characters are what someone actually typed — as likely a truncated entry as a mangled ZIP, and not worth guessing at.

This is, in my experience, the single most common source of "why does Massachusetts geocode to nowhere".

Fail loud on the data file too

One more silent failure worth designing against. When the dataset does not load — wrong path, truncated file, a permissions problem — the natural behaviour is for every lookup to return null. Which reads, from every call site, exactly like we do not cover those ZIP codes.

So the loader reports what it actually loaded, and you assert on it once at startup rather than discovering it one null at a time: 

const { entries, error } = datasetInfo();
if (error) throw new Error(`ZIP centroids unusable: ${error}`);

Worth guarding in CI as well, if the data ships inside the package. A file list that stops matching data/ produces a package that installs cleanly and returns null for everything — and every test still passes, because tests run against the source tree rather than the built artifact. Packing the tarball, installing it into an empty project and geocoding one known ZIP catches it.

This is us-zip-centroids — the Census Gazetteer, the parser above, and a bounds check on every row, since a caller-supplied table can otherwise put somebody at latitude 999.
