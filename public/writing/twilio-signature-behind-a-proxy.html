Four ways a valid Twilio signature looks invalid

13 August 2026 · Webhooks

Signature verification is five lines until you put a reverse proxy in front of it. Then it is four separate bugs that all report the same thing.

Twilio signs its webhooks by computing an HMAC over the exact public URL it is POSTing to, plus the POST parameters. To verify one, you reconstruct that URL from the request you received and check that you get the same signature.

That reconstruction is the whole problem. On a laptop, with the app directly exposed, it is trivial. In production, behind nginx or a load balancer or Cloudflare, the request that arrives at your process no longer resembles the one Twilio sent — and every difference breaks the hash.

There are four of them. They are independent, they can stack, and all four surface as the same line in your logs: invalid signature. Meanwhile your webhook is rejecting real traffic and looking, from the outside, like it is correctly turning away forgeries.

1. The scheme is wrong

Twilio signed https://…. Your TLS terminates at the edge, so by the time the request reaches your app it is plain HTTP and req.protocol says http. Reconstruct with that and every signature fails.

The usual fix is to read X-Forwarded-Proto, which is right until you have two proxies. A chained edge — Cloudflare in front of nginx — sends a list: 

X-Forwarded-Proto: https, http

Take that header at face value and you build https, http://host/path, which is not a URL and matches nothing. Only the leftmost value is the scheme the public client actually spoke.

2. The host is your internal one

nginx passes its own upstream name through unless you explicitly tell it not to, so Host arrives as something like app.internal:3000 rather than the public name Twilio signed. X-Forwarded-Host carries the real one, and it chains the same way, so it needs the same leftmost-value treatment.

3. The path is missing a segment

A proxy rule like this one:

location /sms/ { proxy_pass http://app/; }

strips /sms before your app ever sees the path. Note the trailing slash on proxy_pass — that is what does the stripping, and it is easy to write without meaning to. Twilio signed the URL with that segment; your app reconstructs it without.

4. The query string got dropped

Twilio signs the URL including its query. This matters most for outbound call status callbacks, where the parameters you attached are part of what is signed. In Express, the trap is reaching for req.path or req.url — req.originalUrl is the one that preserves both the mount path and the query.

Every one of these produces a byte-different URL, and HMAC has no notion of nearly. You get one bit of information back — no — for four unrelated causes.

Trusting forwarded headers is fine here

The reflex is that reading X-Forwarded-* is unsafe because a client can forge them. True in general, irrelevant here: an attacker who lies about the scheme or host still cannot produce a signature valid for the URL they claimed. The only request they break is their own. It fails closed either way.

Report which one it was

The single most useful thing you can do is put the reconstructed URL in the log line. When verification fails spuriously it is almost always because that URL is not the one Twilio signed, and seeing it tells you immediately which of the four you have: 

Twilio signature rejected on /api/messages/webhook from 10.0.0.1:
  invalid_signature (http://app.internal:3000/api/messages/webhook)

That line names two of the four at a glance — http where it should say https, and an internal hostname.

Two more that are not URL problems

JSON webhooks are signed differently. For those, Twilio puts a SHA-256 of the body in the URL as a bodySHA256 parameter and signs the URL alone. Feed the parsed JSON in as form parameters — which is what the ordinary path does — and you reject every legitimate request. You need the raw body, captured before parsing: 

app.use(express.json({
  verify: (req, res, buf) => { req.rawBody = buf.toString('utf8'); },
}));

And forgetting the body parser deserves its own error. Signature validation covers POST parameters, so if req.body is undefined the hash cannot match. That is the most common first-run mistake, and it looks exactly like a forgery unless you check for it explicitly and say so.

The 403 that should be a 500

Last one, and it is the one that bites during an incident rather than during setup. These failures are not the same kind of thing:

CauseWhose faultStatus
Missing or bad signaturethe caller's403
Unparsed body, no Hostthe caller's, effectively403
Auth token failed to loadyours500

Collapse them all into 403 and a webhook rejecting all traffic because a secret did not load looks identical to ordinary spam being turned away. Your dashboards show a healthy service declining bad requests. Nobody pages.

Split them — but split by an explicit set of reasons, not by matching strings, and put only failures no request can provoke in the 500 bucket. Otherwise an unauthenticated stranger can manufacture your error budget by choosing what to send.

All of this is in twilio-signature-verify, which does the reconstruction, returns a stable reason code for each failure, and never throws. Its tests sign with the real Twilio SDK rather than a mock, so they exercise the actual algorithm.
