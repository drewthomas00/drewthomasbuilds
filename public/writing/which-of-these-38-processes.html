Which of these 38 processes is eating 20 GB?

13 August 2026 · Debugging

The reload that saves your machine is the same action that destroys the evidence. So I stopped reloading and started sampling.

Every couple of days my editor would climb to fifteen or twenty gigabytes and fall over. The usual advice applies — reload the window, carry on — and it works, which is exactly the problem. Whatever was leaking is gone the instant you recover, and you learn nothing. I did that for months.

The reason it resists casual debugging is that VS Code is not a process. It is thirty to fifty of them: a main process, a GPU process, a renderer per window, out-of-process iframes, the extension host, language servers, whatever your extensions spawn. They mostly share one binary and one name. htop shows you a wall of identical rows summing to 20 GB and tells you nothing about which row matters.

Sample tiers, not processes

Individual PIDs are useless here — they come and go, and a leak that migrates between them looks like noise. What is stable is the tier: renderer, exthost, language server, and so on. Sample the whole tree every 60 seconds, bucket by tier, and the tier that climbs names itself. 

$ vscode-memory-watch --once
VS Code tree: 9589 MB PSS (12622 MB RSS) across 38 processes
  renderer=4942MB exthost=497MB tsserver=346MB langserver=350MB
  helper=191MB nodeutil=567MB gpu=83MB main=155MB
  largest: renderer pid=3369519 at 4360 MB

PSS rather than RSS, incidentally. These processes share a great deal of memory, so summing RSS double-counts heavily and produces a number larger than the machine. Proportional set size divides shared pages among the processes mapping them, so the tiers actually add up.

What four hours said

The tree went from 3.8 GB to 7.5 GB — roughly a gigabyte an hour. The split:

TierBehaviour
renderer+2361 MB — 64% of all growth
tsserverpeaked at 1784 MB, returned to 442 MB
exthost+49 MB net
agent sessions~265 MB each, flat per session

tsserver is the instructive one. It grew by a gigabyte and a third and then gave it all back — that is a working set, not a leak, and staring at a point-in-time snapshot it would have looked like the obvious culprit. Only the shape over time separates the two.

The renderer tier did not give it back. And it was not the tier leaking — it was one process in it: 924 MB to 3121 MB, a monotonically rising floor with ordinary GC sawtooth riding on top. The window's own renderer sat beside it at a stable 248 MB the whole time.

A rising floor under a sawtooth is the signature worth learning. Garbage collection is working perfectly — memory is released on every cycle — but the low-water mark after each collection is higher than the last. Something is holding a reference it should have dropped.

The offending process turned out to be an out-of-process iframe hosting a chat panel, spawned with no heap cap, retaining every message ever rendered. That matched an open upstream issue exactly, and several older ones describing the same shape. Which is the useful outcome: not a fix I could apply, but a specific, evidenced thing to point at instead of "the editor leaks."

Ruling things out is most of the work

The sampling also killed three theories I had been carrying, each in one measurement:

  • Not the system OOM killer. 62 GB of RAM, zero OOM kills in the journal, systemd-oomd inactive. The editor was dying on a per-process V8 heap limit, which is a completely different failure with completely different fixes.
  • Not a runaway loop. 22 hours of extension logs showed ~2,900 ordinary API turns and no repeating error storm.
  • Not session restore. A fresh session sat at 238 MB; one resuming a 224 MB transcript sat at 295 MB. Strongly sublinear — so growth was live accumulation, not loading history.

Anchor on the thing only a real instance has

One implementation detail worth stealing, because getting it wrong corrupts the data silently.

The obvious way to find the process tree is to pattern-match the main process by its command line. That breaks in a way you will not notice: code --wait, used as your $GIT_EDITOR, spawns Chromium children and matches every pattern a real main process does. Adopt it as an instance and — since a change in the set of main processes is what ends a measurement run — a routine git commit silently discards hours of accumulated curve.

So instead: find every renderer, walk up to whatever owns it, and check that the owner looks like an editor before walking back down. A renderer is the one thing only a real editor instance has. That check matters twice over, because every Electron app has renderers — without it, Signal or Obsidian running on the system electron binary gets adopted, merged into your totals, and ends your run when the user quits it.

The walk stops at anything that is not a known VS Code process type, and skips anything with a controlling terminal — except the terminal the editor was launched from. An extension's language server counts; the cargo build you started in the integrated terminal does not. That is your memory, not the editor's, and sweeping it in would inflate the headline and fire the alert for the wrong reason.

The point

I did not fix this bug. It is upstream and it is still open. But "VS Code eats 20 GB" — a complaint with nothing actionable in it — became "this specific process grows one gigabyte an hour with a monotonic floor, here is the CSV," which is a thing a maintainer can act on and a thing I can plan around.

The general version: when the recovery action destroys the evidence, instrument before you recover. It took an afternoon of sampling to answer a question I had been guessing at for months.

vscode-memory-watch is the sampler — a bash script and a systemd user unit, no dependencies beyond coreutils and /proc. It warns before the crash and dumps a full snapshot at the moment things go bad, so the evidence outlives the reload.
